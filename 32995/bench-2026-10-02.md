# #32995 bench, 2026-10-02: the failed flight, two bugs, CPU load A/B

Andy flew `rp2350-flight-test` at `df0ee89f` (PR head `564e6c1c7d` plus 17
split-out commits). It did not fly: the board rebooted continuously. With
the lock-free clock (`2d147f576d`) backed out the reboots stopped, but the
GPS kept dropping out. Both causes were found on the bench on RPI_UAVFC
(COM5, picoprobe SWD), neither of them the clock.

## 1. The reboots: the PIO UART lock deadlocked core0

Read over SWD without halting:

- `rp2350_wd_reset_detected` 1, saved persistent data with no fault
  address: a watchdog lockup, not a fault. `scheduler_task` -3: the main
  thread was in `AP::ins().wait_for_sample()` when it fired.
- On the board as found (watchdog not yet armed that boot, `WATCHDOG->CTRL`
  `0x07000000`), core0's PC sat at `0x20080ba6`/`0x20080baa` in
  `PIORXDriver::_service_irq()`, the `ldaex`/`strex` spin, for 15 s of 0.5 s
  samples. Core1 was in `rp2350_idle_c1`.
- `serial3Driver` (`0x20026340`, lock at +0x7c) lock word: 1.
- Halted core0: IPSR 31 (PIO0 IRQ0), BASEPRI 0, EXC_RETURN `0xffffffed`
  into a thread on PSP. The stacked thread PC `0x1016d934` is in
  `PIORXDriver::_write()` between `_lock_thread()` and `_unlock_thread()`.

The thread held the lock with BASEPRI raised only to `PIO_UART_IRQ_PRIO`
(0x50). Kernel interrupts at priorities 2-4 still ran inside the section,
and every one that leaves through `chSysUnlockFromISR()` goes through
`port_unlock()`, which writes BASEPRI 0 (`ARMv8-M-ML/chcore.h`). The
port's own interrupt then preempted the lock holder on its own core and
spun for ever. Before the watchdog is armed that is a hang; after, a reboot
loop.

Fix: `_lock_thread()` raises BASEPRI to `CORTEX_BASEPRI_KERNEL` (0x10), the
local mask `chSysLock()` uses, still without the cross-core spinlock. With
it, and the clock change still in, 3 minutes with no reboot and no
heartbeat gap over 1 s.

## 2. The GPS: an aborted RP2350 DMA channel reads TRANS_COUNT as 0

The GPS is SERIAL2, hardware UART1 (GPIO36/37), with RX DMA. Symptom:
"detected u-blox", then lost and re-probed about every 12 s, with UART1
`RXDRP` 20673 over the first window and 384 over the next 10 s, and RX at
about 7 kB/s.

The 1 kHz partial-buffer flush aborts the RX channel and, since
`afd3275fb5` (automated review #1, finding 6), re-reads `TRANS_COUNT` after
the abort. Tested on the chip with both cores halted: UART1 RX channel 3
had written 7 bytes (`WRITE_ADDR` `...ef0` -> `...ef7`) and read
`TRANS_COUNT` 0 straight after `CHAN_ABORT`. A timer-paced test channel
showed the same with `READ_ADDR`: offset 1 kept, `TRANS_COUNT` 0. So every
flush wrote the whole 64-byte bounce buffer, real bytes plus stale ones,
into the ring.

Fix: count from `WRITE_ADDR` in both branches of the flush; the TX timeout
path had the same read and now counts from `READ_ADDR` (that one predates
the review fix and is not bench-tested: it needs a TX timeout). After the
fix: detected once at 8.5 s with the version and protocol messages (absent
before), no re-probe in 150 s, UART1 RX about 1.1 kB/s, `RXDRP` 0 over a
10 s window.

## 3. CPU load A/B

One boot per build, on battery, props off, motors powered, bidirectional
DShot RPM returned in every armed run. Busy = share of DWT PCSR samples
(about 60,000 per core per state, 20 s) outside `rp2350_idle_c0/c1`.
Load is SYS_STATUS (main loop).

| | A: PR before 2026-10-01 `2b8df6d7` | B: PR head + the two fixes `3e60038d` | flight-test + fixes `c3c34395` |
|---|---|---|---|
| core0 disarmed | 68.3% | 68.6% | 75.3% |
| core0 armed | 71.0% | 71.7% | 71.3% |
| core1 disarmed | 47.8% | 46.8% | 47.8% |
| core1 armed | 56.6% | 56.1% | 52.0% |
| load armed | 50.5% | 50.0% | 53.7% |

A and B agree within about a point everywhere, the same top functions on
both cores: 2026-10-01's changes cost nothing measurable. The rate thread
held 1608 Hz ("Rate CPU normal") on `c3c34395`. Its lower core1 armed load
fits the branch's extra notch loop-rate commit (#34436); its higher core0
disarmed load is either the 17 extra commits or boot-to-boot variation,
which one boot per build cannot separate. ESC temperatures read 0 in every
run (EDT not enabled, not checked).

## 4. What made this possible to miss

- The 2026-10-01 PIO UART check was "u-blox detection works", on a board
  where the u-blox is on a hardware UART. It never exercised the PIO lock.
- The deadlock needs a kernel interrupt to land inside a few-microsecond
  section and the port's interrupt to follow before the unlock; it took
  seconds on a flying-configuration board with ELRS on the PIO UART, and
  did not show in the 2026-10-01 bench boots.
- The `TRANS_COUNT` re-read was a review fix reasoned from the code, never
  run against an abort on the chip.
