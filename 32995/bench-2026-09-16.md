# Bench session, 2026-09-16: OSD starvation reproduced props-off

Andy's analog-OSD quad (RPI_UAVFC, board id 7160), USB MAVLink through a
Windows COM-to-TCP bridge, no RC. Firmware: the round-two field build
`35e92d8b` ([field-test-round2.md](field-test-round2.md)).

## What was measured

The new report worked on hardware: every line fits the log, `uarts.txt` has
PIO rows (SERIAL3, nothing connected, shows steady framing errors).

| State | core1load | OSD late blocks / 10 s | Rate loop | core0load |
|---|---|---|---|---|
| Disarmed | 53-55% | 0 (a few when a flash write parks core1) | 1604 Hz | 44-46% |
| Armed, motors spinning (run 2, four windows) | **96%** | **~14,800 of 15,600 (95%)** | 1604 Hz, dtMax <= 1.2 ms | 59-60% |

NTSC, 26 blocks per field. So while armed the overlay is almost entirely
blank, and nothing else misses a deadline: the OSD renderer is the lowest
priority thread on core1 and absorbs all of the shortfall. This is the
tester's symptom.

Also seen: free heap 13 KB after arming (largest block 7 KB) on the field
build; the io thread (priority 58, core0) stalled ~10 s just after arming in
both runs, so the report due then never ran.

## How the test went wrong

Run 2 armed in STABILIZE with RC-override throttle at mid-stick, props off. The
drone sat 2.4 deg tilted, the roll and pitch I-terms wound to their limits, and
output 2 was pinned at full (RCOU 1950, ~40,000 RPM unloaded) with output 3 at
minimum for ~50 s (~10 s in run 1). The bench supply then tripped and kept
tripping; the quad is out of action pending a hardware check. Armed bench runs
must be at zero throttle only.

Whether the 96% depends on that saturation is not separately measured; the
work that arming adds does not scale with throttle (below), so it probably
does not.

## What arming adds to core1 (code, plus partial profile evidence)

The motor mixer and servo output run every rate tick armed or not
(`AP_MotorsMulticopter::output()` is unconditional), so they are not the
difference. What arming does change:

1. **Per-motor harmonic notch updates at 1604 Hz.** In ESC-RPM mode with
   `DynamicHarmonic`, each spinning motor gets its own notch set, and while
   RPM moves every filter recomputes its coefficients (`sinf`, `cosf`, three
   `is_equal` calls). The fast rate thread calls `update_dynamic_notch()` at
   `filter_rate` = raw gyro rate / 2, which is every rate tick; the
   non-fast-rate path decimates to 200 Hz unless `LoopRateUpdate` is set. The
   rate thread ignores that option. This is master behaviour, not the port's.
   - bench quad: `INS_HNTCH_OPTS 22` (per-motor, loop-rate, triple), `HMNCS 7`
     -> 4 x 3 x 3 = 36 filters -> ~57,700 coefficient updates/s
   - tester: `OPTS 2`, `HMNCS 3` -> 8 filters -> ~12,900/s
   - evidence: while armed, two PCs in the veneer to `is_equal<float,float>`
     (XIP flash, called from SRAM) rose into the core1 top 16;
     `HarmonicNotchFilter::set_center_frequency` and `NotchFilter::apply` are
     among the hottest core1 functions over the session.
2. **Logging written from core1.** With `LOG_DISARMED 0`, arming starts the
   rate thread's fast attitude/PID logging (bench `LOG_BITMASK` has
   ATTITUDE_FAST and PID), the batch sampler (bench `INS_LOG_BAT_MASK 3`,
   tester 1) and raw gyro logging (tester `INS_RAW_LOG_OPT 9`). All take the
   logger semaphore from core1; `port_spinlock_take` and `chSchGoSleepS` were
   in the armed top 16, and on the tester `Write_GYR` alone was 2.8% of core1
   over a session one third in flight.
3. **DShot telemetry decode with real eRPM** - present disarmed too, so
   probably a small change.

An attempt to difference a mostly-disarmed session histogram against a
disarmed-only one gave per-function numbers too noisy to use (the idle PC
saturates at 65535 and the baselines came from different stretches of uptime).
Not quoted.

On RP2350 the dynamic fast rate (`FSTRATE_ENABLE 2`) cannot see this: the PR
made the rate check ignore main-loop overruns when the cores are independent,
and the rate thread itself never runs slow, so it never backs off while the
OSD starves.

## Best guess at the fix

Config the tester can try now, in order of expected effect:

1. Logging off core1: `INS_RAW_LOG_OPT 0`, `INS_LOG_BAT_MASK 0`, and keep
   ATTITUDE_FAST (1) and PID (4096) out of `LOG_BITMASK`.
2. Fewer notch filters: `INS_HNTCH_OPTS 0` tracks the average ESC RPM with one
   notch per harmonic (2 filters at `HMNCS 3`) instead of one set per motor
   (8). This is a filtering trade-off; check the gyro spectrum afterwards.
3. If the OSD still drops out: `FSTRATE_DIV 4` for a ~800 Hz rate loop, which
   halves both the rate thread and the notch update rate.

Code, as additive commits:

1. Honour `LoopRateUpdate` in the fast rate thread: update notch centres at
   200 Hz unless the option is set, as the ordinary path already does. 8x
   fewer coefficient updates on both quads. Touches master behaviour, so it
   may belong in its own upstream PR.
2. OSD renderer: send all-blank character rows without rendering them, so the
   renderer's demand drops with how empty the screen is.
3. Only after measuring 1 and 2: whether `OSD_c1` should sit above `rcout`, or
   whether the dynamic fast rate should back off on core1 load.
4. Minor: `is_equal` is a non-inline template reached from SRAM through an
   XIP veneer on every notch update.

Each of these is checkable with the round-two counters: `core1load` and
`OSD: late=` per 10 s window, armed at zero throttle.
